# `withFunding`

Discovers omitted funding sources before filling a transaction with gas, fees, and a nonce.

## Usage

```ts
import { createClient, http, parseUnits } from 'viem'
import { tempo } from 'viem/chains'
import { Addresses, tempoActions, withFunding } from 'viem/tempo'
import { account } from './account'

const client = createClient({
  account,
  chain: tempo,
  transport: withFunding(http()),
}).extend(tempoActions())

// The transfer supplies the token and amount; the transport discovers sources.
await client.token.transferSync({
  amount: parseUnits('50', 6),
  requireFunds: true,
  to: '0x742d35Cc6634C0532925a3b844Bc9e7595f0bEbb',
  token: Addresses.pathUsd,
})
```

The account must hold a fee token or use a fee payer. Funding supplies application balances, not transaction fees.

## Parameters

### transport

- **Type:** `Transport`

Downstream transport supporting `eth_fillTransaction` and the funding discovery contract. For sponsorship, wrap the relay transport with `withFunding` so discovery runs before sponsor signing.

### parameters.getRoute

- **Type:** `({ chainId, token, transaction }) => Route | undefined | Promise<Route | undefined>`

`transaction` is the unsigned RPC request. Use `transaction.from` to select routes for the funding account; it contains an address, not a local signer.

Optional callback returning ordered source configurations and `slippageBps` for a chain and output token. The token address is checksummed. Return `undefined` to reject discovery for that pair. Explicit sources bypass the callback.

By default, mainnet and testnet use Viem's known tokens with the same currency as the output, excluding the output itself. Localnet uses PathUSD, AlphaUSD, BetaUSD, and ThetaUSD. Inputs have no source-specific cap. Unknown output tokens and other chains, including Zones, require a custom callback.

```ts
import { http } from 'viem'
import { Addresses, FundingSource, withFunding } from 'viem/tempo'

withFunding(http(), {
  getRoute: async ({ chainId, token }) => {
    if (chainId !== 42431 || token !== Addresses.pathUsd) return undefined
    return {
      slippageBps: 100,
      sources: [FundingSource.dex({ tokenIn: Addresses.alphaUsd })],
    }
  },
})
```

Explicit transaction slippage takes precedence over the route default. If both are omitted, slippage is zero. Each requirement has its own aggregate tolerance. Known tokens are discovery inputs, not a guarantee of balances, liquidity, or deployed funding support.

The transport passes the client's configured chain ID to the handler. The handler uses the explicit request-option chain ID or the transaction's chain ID and rejects conflicts. When neither is supplied, it defaults to Tempo mainnet (4217). Discovery and filling receive the resolved chain ID in request options.

### parameters.store

- **Type:** `Store.Store`

Optional store for funding policy rules. Defaults to an in-memory store per transport. Rules are keyed by chain, policy contract, and rules hash; each request still reads the policy's current commitment.

```ts
import { http } from 'viem'
import { Store, withFunding } from 'viem/tempo'

withFunding(http(), { store: Store.memory() })
```

## Access Key Funding

Access key transactions use the key's funding policy, not `getRoute`. The handler resolves installed keys and signed key authorizations with existing or inline policies, then inserts verified `policyRules`. Explicit sources and input caps remain unchanged.

`createPolicy`, `setPolicyRules`, and inline access key authorization register rules with the handler through `funding_registerPolicyRules`. Supplied rules are also cached after verification against the current commitment. Configure persistent handler storage when rules must survive restarts. The same registration method works with a remote relay.

If the store does not contain the current rules, supply `policyRules` explicitly. The handler does not scan event history. Expired, revoked, or policy-less keys cannot use owner routes.

The node validates authorization signatures, permissions, and spending limits during filling and execution. Policy changes between filling and execution can invalidate the transaction's rules. Discovery does not reserve funds.

## Behavior

Token transfers, burns, and exact-input DEX sells accept `requireFunds: true`. These actions infer the spent token and amount before calling the transport. Generic transactions still need explicit token and amount requirements.

- Omitted `requireFunds` and `[]` perform no automatic funding.
- Omitted `sources` use the output token's configured route. A missing route fails.
- Explicit sources, including `[]`, retain their order, caps, and data.
- Discovery precedes gas estimation and signing. Discovery does not reserve funds.
- Filling errors are propagated. Incomplete requirements cannot fall back to signing.

## Return Value

The original transport type and metadata, with a `funding: true` marker. The wrapper uses [`Funding.handleRequest`](/tempo/utilities/Funding.handleRequest), which can also run in a server relay.
