# Funding Transactions

## Overview

`requireFunds` specifies token balances to satisfy before transaction calls execute. Existing balances count toward each requirement. Funding sources run in order to supply the shortfall, and funding reverts with a failed payment.

This preview requires a TIP-1120-enabled node. It does not enable funding on public networks. Source addresses must match the target deployment.

## Recipes

These recipes assume you have [set up a Tempo client](/tempo).

### Fund a Transaction

Use [`sendTransaction`](/docs/actions/wallet/sendTransaction) with complete requirements. `FundingSource.dex` creates a native DEX source with its address and encoded data. This example sources up to 30 pathUSD, then uses USDC.e for the remaining OUSD shortfall.

:::code-group

```ts [example.ts]
import { parseUnits } from 'viem'
import { Addresses, Actions, FundingSource } from 'viem/tempo'
import { client } from './viem.config'

const ousd = '0x...' // Output token address.
const usdcE = '0x...' // Second input token address.

await client.sendTransaction({
  calls: [
    Actions.token.transfer.call({
      token: ousd,
      to: '0x...',
      amount: parseUnits('50', 6),
    }),
  ],
  requireFunds: [{
    token: ousd,
    amount: parseUnits('50', 6),
    slippageBps: 100,
    sources: [
      FundingSource.dex({
        tokenIn: Addresses.pathUsd,
        maxAmountIn: parseUnits('30', 6),
      }),
      FundingSource.dex({ tokenIn: usdcE }),
    ],
  }],
})
```

:::

### Fund an Action

Tempo write actions accept `requireFunds`. For actions with an exact input, the action can infer the requirement's `token` and `amount`. This transfer funds the required OUSD balance before sending it.

:::code-group

```ts [example.ts]
import { parseUnits } from 'viem'
import { Addresses, FundingSource } from 'viem/tempo'
import { client } from './viem.config'

const ousd = '0x...' // Output token address.

await client.token.transferSync({
  token: ousd,
  to: '0x...',
  amount: parseUnits('50', 6),
  requireFunds: [{
    slippageBps: 100,
    sources: [FundingSource.dex({ tokenIn: Addresses.pathUsd })],
  }],
})
```

```ts [viem.config.ts]
// [!include ~/snippets/tempo/viem.config.ts:setup]
```
:::

`token.transfer` (without `from`), `token.burn`, and `dex.sell` infer the spent token and exact amount. Their `Sync` variants do the same. Other actions, including `earn.deposit`, need explicit `token` and `amount`; either field can always be supplied to override an inferred value.

### Discover Funds

Use [`funding.discover`](/tempo/actions/funding.discover) with source configurations describing the sources to search. Owner-authorized funding needs no stored policy. The returned requirement can be passed directly to the transaction.

:::code-group

```ts [example.ts]
import { parseUnits } from 'viem'
import { Addresses, FundingSource } from 'viem/tempo'
import { client } from './viem.config'

const discovery = await client.funding.discover({
  account: client.account.address,
  amount: parseUnits('50', 6),
  slippageBps: 100,
  sources: [FundingSource.dex({ tokenIn: Addresses.alphaUsd })],
  token: Addresses.pathUsd,
})

await client.token.transferSync({
  amount: parseUnits('50', 6),
  requireFunds: [discovery],
  to: '0x742d35Cc6634C0532925a3b844Bc9e7595f0bEbb',
  token: Addresses.pathUsd,
})
```

```ts [viem.config.ts]
// [!include ~/snippets/tempo/viem.config.ts:setup]
```
:::

Supply `policyId` and `rules` instead of `sources` and `slippageBps` to discover and verify the rules against a stored policy's current hash. Obtain those rules from creation or update events, or an indexer. Discovery includes the supplied `rules`, so its result can also fund an access key transaction.

Discovery reports current availability but does not reserve it. `availableAmount` is advisory and is omitted from transaction encoding.

### Fund with an Access Key

Authorize the access key with a funding policy and a spending limit for the payment token. An inline policy creates a new policy when the key is installed; use `fundingPolicy: policyId` to bind an existing policy.

:::code-group

```ts [example.ts]
import { generatePrivateKey } from 'viem/accounts'
import { parseUnits } from 'viem'
import { Account, Addresses, FundingSource } from 'viem/tempo'
import { client } from './viem.config'

const accessKey = Account.fromP256(generatePrivateKey(), {
  access: client.account,
})

const { policyId, rules } = await client.funding.createPolicySync({
  admins: [client.account.address],
  rules: {
    maxSlippageBps: 100,
    sources: {
      [Addresses.pathUsd]: [FundingSource.dex({ tokenIn: Addresses.alphaUsd })],
    },
  },
})

await client.accessKey.authorizeSync({
  accessKey,
  fundingPolicy: policyId,
  limits: [{ token: Addresses.pathUsd, limit: parseUnits('50', 6) }],
})

await client.token.transferSync({
  account: accessKey,
  amount: parseUnits('50', 6),
  requireFunds: [{
    rules,
    sources: [FundingSource.dex({ tokenIn: Addresses.alphaUsd })],
  }],
  to: '0x742d35Cc6634C0532925a3b844Bc9e7595f0bEbb',
  token: Addresses.pathUsd,
})
```

```ts twoslash [viem.config.ts] filename="viem.config.ts"
// [!include ~/snippets/tempo/viem.config.ts:setup]
```

:::

Pass `rules` as a decoded object or ABI-encoded hex. Viem encodes it into `policyRules` for access key execution and omits it for owner-authorized execution. Do not supply both fields.

Omitting `slippageBps` uses the policy maximum. An explicit value cannot exceed it. Funding cannot pay transaction fees; the account needs a fee balance or a fee payer, and call scopes must allow the payment.

Read an installed key's policy ID with [`accessKey.getFundingPolicyId`](/tempo/actions/accessKey.getFundingPolicyId). For discovery, supply that ID and current rules, then pass the result directly as `requireFunds: [discovery]`.

Policy updates invalidate previously encoded rules. Obtain current rules from creation/update events or your indexer and sign a new transaction; Viem does not rewrite signed requirements or automatically retry with different permissions.

For inline installation and payment in one transaction, use `accessKey.signAuthorization` and pass the signed `keyAuthorization` with the access key transaction. Funding and payment revert together, but key and inline-policy installation can persist when a later payment reverts.

## Best Practices

- Requirements specify target balances, not additional amounts. Repeated token entries are processed in order.
- `slippageBps` applies across all sources in a requirement. Zero allows no aggregate loss; omission uses the protocol default.
- Source caps use input token base units. Omitting `maxAmountIn` allows the maximum input amount, subject to protocol limits.
- Funding cannot pay transaction fees. Hold a supported fee token or use [fee sponsorship](/tempo/guides/sponsor-fees).
- Owner-authorized execution omits discovery `rules` from the signed transaction. Explicit `policyRules` remains a protocol field for access key funding.

Gas is estimated automatically. Tests that intentionally submit reverting transactions supply a gas limit to bypass estimation and verify onchain rollback.
